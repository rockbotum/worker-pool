## Что это

Компактная реализация **пула воркеров** (worker pool) — классического паттерна для ограничения конкурентности при большом потоке задач.

Вместо `go func()` на каждую задачу пул держит фиксированное число горутин и раздаёт им работу из буферизованной очереди. Это даёт предсказуемую нагрузку на CPU, память и внешние сервисы.

Особенности реализации:

- **Результат через канал** — `Submit` возвращает канал, который получит `Result` (аналог `Future` / `Promise`)
- **Изоляция паник** — `recover` превращает панику в `Result.Error`, пул продолжает работать
- **Graceful shutdown** — `Stop(timeout)` дорабатывает очередь, но не зависает навсегда
- **Отмена через `context.Context`** — отмена контекста останавливает приём новых задач

## Архитектура

```
                    ┌──────────────────────────────────────┐
   Submit(task) ───▶│  taskQueue  (chan queuedTask, буфер N) │
   ◀── chan Result   └───────────────┬──────────────────────┘
       + taskID                      │  N воркеров
                    ┌───────────────▼──────────────┐
                    │  worker 0 │ worker 1 │ ...    │
                    │    ↓ Task.Execute()           │
                    │    ↓ recover(panic)           │
                    │    ↓ Result{Value, Err, ID}   │──▶ result-канал задачи
                    └──────────────────────────────┘
```

Задача проходит путь: **очередь → свободный воркер → `Execute()` → `recover` → отправка результата в персональный канал**.

## Запуск


Демо-точки входа нет — `main.go` пуст, проект используется как библиотека.

## Использование

```go
type MyTask struct {
    userID int
}

func (t MyTask) Execute() (any, error) {
    // тяжёлая работа: запрос в БД, вызов API, чтение файла
    return doWork(t.userID)
}

pool := NewWorkerPool(8, 100) // 8 воркеров, очередь на 100 задач
if err := pool.Start(ctx); err != nil {
    log.Fatal(err)
}
defer pool.Stop(10 * time.Second)

for _, id := range userIDs {
    ch, taskID, err := pool.Submit(MyTask{userID: id})
    if err != nil {
        log.Printf("submit %d failed: %v", id, err)
        continue
    }

    go func(taskID int, ch <-chan Result) {
        res := <-ch
        if res.Error != nil {
            log.Printf("task %d failed: %v", taskID, res.Error)
            return
        }
        log.Printf("task %d ok: %v", taskID, res.Value)
    }(taskID, ch)
}

log.Printf("в очереди: %d, воркеров: %d", pool.PendingTasks(), pool.ActiveWorkers())
```

## API

### Конструктор

```go
func NewWorkerPool(workerCount int, queueSize int) workerPool
```

| Параметр | Назначение |
| --- | --- |
| `workerCount` | сколько горутин-воркеров запустить |
| `queueSize` | размер буфера очереди; задачи сверх лимита блокируют `Submit` |

### Интерфейс `WorkerPool`

| Метод | Поведение |
| --- | --- |
| `Start(ctx) error` | Запускает воркеров. Повторный вызов — no-op. Контекст управляет остановкой |
| `Submit(task) (<-chan Result, int, error)` | Кладёт задачу в очередь. Возвращает канал результата и `TaskID` (`-1` при ошибке) |
| `Stop(stopTimeout) error` | Закрывает очередь, дорабатывает её и ждёт воркеров. `context.DeadlineExceeded` при таймауте |
| `ActiveWorkers() int` | Сколько воркеров считается активными |
| `PendingTasks() int` | Текущая длина очереди |

### Типы

```go
type Task interface {
    Execute() (any, error)
}

type Result struct {
    Value  any
    Error  error
    TaskID int
}
```

## Ключевые решения

**`chan Result` с буфером 1, а не мьютекс.** Каждый результат уходит в собственный канал, поэтому воркер не блокируется, даже если вызывающий код ещё не забрал предыдущий результат. Обратная сторона: если читатель не заберёт значение — утечка горутины воркера.

**`recover` внутри анонимной функции.** Паника в задаче не должна убивать весь пул. `defer` ловит её, отправляет `Result{Error: fmt.Errorf("panic: %v", r)}` и закрывает канал — воркер продолжает цикл.

**Закрытие `result` в обоих ветках.** Канал результата закрывается и при панике, и при нормальном завершении. Это даёт потребителю возможность отличить «результат получен» от «канал пуст».

**`Stop` закрывает очередь, а не отменяет контекст.** Ранняя отмена уводила бы воркеры, бросая задачи из очереди. Закрытие канала даёт graceful drain: воркеры дочитывают остаток и завершаются. Контекст отменяется уже после `wg.Wait()` — как страховка на случай зависших задач.

**`mu` защищает только состояние пула.** Счётчик `nextTaskID` и флаги `started` / `stopped` защищены мьютексом; сама очередь синхронизирована каналом.

## Гарантии и семантика

| Свойство | Поведение |
| --- | --- |
| Порядок выполнения | **не гарантируется** |
| Изоляция ошибок | ошибка задачи → `Result.Error`, пул работает дальше |
| Изоляция паник | паника задачи → `Result.Error`, пул работает дальше |
| Переполнение очереди | `Submit` **блокируется** (backpressure) |
| Повторный `Start` | no-op, возвращает `nil` |
| Повторный `Stop` | no-op, возвращает `nil` |
| `Submit` после отмены ctx | ошибка, `TaskID = -1`, канал закрыт |

## Известные ограничения

- **`Submit` отправляет в очередь под мьютексом** (worker_pool.go:95). Если очередь переполнена, `Submit` блокируется, удерживая `mu`, и `Stop` не сможет взять мьютекс. На практике это backpressure, но при зависших воркерах `Stop` тоже зависнет.
- **`NewWorkerPool` возвращает значение структуры**, а не `*workerPool`. Копирование структуры с `sync.Mutex` небезопасно — безопаснее возвращать указатель.
- **Утечка при таймауте `Stop`.** Если задача не завершается, воркер и горутина `wg.Wait()` остаются жить. Нужен `recover`-таймер или прерываемые задачи.
- **`Task` не принимает `context.Context`.** Задачу нельзя отменить — только дождаться её завершения.
- **Отмена контекста может оставить задачи в очереди.** Воркер выбирает между `<-ctx.Done()` и чтением очереди; при отмене он может уйти, не забрав задачи.
- **Нет поддержки приоритетов и повторной постановки.** Упавшая задача не возвращается в очередь автоматически.

## Возможные улучшения

- `Task.Execute(ctx context.Context)` — чтобы задачи поддерживали отмену.
- Отдельный метод `StopGraceful(ctx)` против `StopNow()`.
- Счётчики метрик: обработано задач, в очереди, среднее время выполнения.
- Ограничение параллелизма по ключу (например, по `userID`), чтобы не блокировать параллельные операции над одним объектом.
- Выгрузка воркеров через `errgroup` вместо ручного `WaitGroup`.

## Назначение

Учебный / reference-проект по конкурентному программированию на Go: пул воркеров, буферизованные очереди как точка backpressure, передача результата через канал, изоляция паник, graceful shutdown. Полезен как основа для обработки параллельных задач с ограничением по ресурсам.
